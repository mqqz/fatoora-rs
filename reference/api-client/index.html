    ZATCA API client¶

    The API client requests credentials and submits signed invoices to the selected environment. For a runnable integration, start with the API guide. This reference describes inputs, returned data, and how to distinguish a completed request from an accepted invoice.

    Choose an operation¶

    Operation Required input Returns Behavior
    Issue compliance credentials CSR and OTP Compliance credentials (CCSID) Sends the CSR as Base64-encoded PEM.
    Issue production credentials Compliance credentials with a request ID Production credentials (PCSID) Uses the compliance request ID to request production credentials.
    Renew production credentials Existing production credentials, new CSR, OTP, response language Production credentials Submits a renewal request.
    Check invoice compliance Signed invoice and compliance credentials Validation response Checks the invoice; a passing check does not establish reporting or clearance.
    Report a simplified invoice Signed simplified invoice, production credentials, clearance flag, response language Validation response Rejects standard invoices before sending.
    Clear a standard invoice Signed standard invoice, production credentials, clearance flag, response language Validation response Rejects simplified invoices before sending.

    Credentials must match the client's environment. Production credentials describe the credential scope; they can belong to a test environment. The credential constructor stores supplied values; it does not authenticate them or obtain a certificate. Preserve the request ID returned during compliance onboarding.

    Input values¶

    Input Expected value Notes
    Configuration Selected environment Used for endpoints and credential environment checks.
    CSR Parsed or generated certificate signing request See CSR reference. Supply the matching private key separately when signing invoices.
    OTP Text supplied for the onboarding or renewal operation Sent in the OTP header. Invalid HTTP-header characters fail before transport.
    Token Binary security token returned by ZATCA Used with the secret for HTTP Basic authentication.
    Secret Credential secret returned by ZATCA Keep credentials out of logs.
    Request ID Optional text from credential issuance Required to request production credentials from compliance credentials.
    Invoice Signed invoice object The client sends its hash, UUID, and Base64 XML.
    Clearance flag Boolean Sends Clearance-Status: 1 when true, 0 when false. It does not change the selected operation.
    Response language ar, en, or omitted Only the exact value ar selects Arabic; every other value sends English.

    Interpret an invoice response¶

    A successful HTTP status means that a response body was decoded. Check acceptance before treating an invoice as reported or cleared. The acceptance helper fails for both rejected and unknown outcomes.

    Invoked operation Accepted status Rejected status
    Reporting REPORTED NOT_REPORTED
    Clearance CLEARED NOT_CLEARED
    Compliance Validation status PASS or WARNING Validation status ERROR

    Missing or unrecognized endpoint status produces an unknown outcome. A positive status accompanied by validation errors also produces an unknown outcome. Warnings alone do not prevent acceptance. Only the status for the operation actually invoked determines its outcome.

    Returned field Value Meaning
    HTTP status Optional integer Actual response status, when attached by the client.
    Outcome Accepted, rejected, or unknown Classification for the invoked operation.
    Validation results Result object Contains message collections and optional overall status.
    Reporting / clearance status Optional text Raw gateway status for each operation.
    Seller / buyer QR status Optional text Raw QR status returned by the gateway.
    Cleared invoice Base64 Optional text Exact encoded invoice returned by clearance.
    Cleared invoice XML Optional decoded text Preserves returned text; does not parse XML or verify its signature.

    Missing cleared XML is independent of acceptance. A present empty Base64 value, invalid Base64, NUL bytes, or invalid UTF-8 fails decoding.

    Validation results contain information, warning, and error message collections, which can be empty, plus an optional status. Each message has optional type, code, category, message text, and status fields. Handle missing fields instead of assuming that every response contains a complete diagnostic.

    HTTP failures and custom transport¶

    Invoice operations treat every non-2xx response as an error, including 400 and 409. A duplicate-reporting 409 does not establish that an earlier submission was rejected. A 208 clearance response follows the successful-response path and still requires an acceptance check. Redirects are not followed; a 303 does not trigger automatic reporting. A malformed successful body is a decoding error, and a failed body read is a transport error.

    Credential issuance requires a successful response. Renewal additionally supports the gateway's 428 renewal response when it contains a decodable credential body.

    Where exposed, prepared requests let you use your own HTTP transport. Preparing performs input checks and builds an owned request without sending it. Send its method, URL, headers, and body, then pass the actual HTTP status and response bytes to its decoder. Headers contain credentials. The decoder preserves the operation context needed for acceptance checks. Keep redirects disabled in custom transports.

    Prepared requests

    Prefix each HTTP method above with prepare_ and use the same arguments. These synchronous methods return Result<ComplianceRequest, ZatcaError> for CSR issuance, Result<ProductionRequest, ZatcaError> for production issuance/renewal, and Result<InvoiceRequest, ZatcaError> for invoice operations.

    prepared.request() borrows an HttpRequest. Its method() and url() return &str, headers() returns &[(String, String)], and body() returns &[u8]. prepared.decode(status: u16, body: &[u8]) returns the corresponding response or credentials in Result<_, ZatcaError>. Preparing and decoding do not consume inputs. The request owns its data and can outlive the client, invoice, and credentials.

    Import ZatcaClient, CsidCompliance, CsidProduction, and InvoiceOutcome from fatoora. Construct ZatcaClient(config: Config). HTTP calls block until they finish and raise classified exceptions on failure; see errors.

    Prepared requests

    For custom transport, import ZatcaClient as RequestClient from fatoority/raw and create it with RequestClient.create(config). Its synchronous methods are preparePostCsrForCcsid, preparePostCcsidForPcsid, prepareRenewCsid, prepareCheckInvoiceCompliance, prepareReportSimplifiedInvoice, and prepareClearStandardInvoice. They take the same operation arguments as above, without options; supply the clearance boolean and nullable language explicitly. They return ComplianceRequest, ProductionRequest, or InvoiceRequest according to the operation.

    request.method(), url(), and headersJson() return strings; body() returns Bytes. request.decode(status, body) takes an HTTP status number and an array of byte numbers and returns the corresponding credentials or validation response. Alternatively, await sendPrepared(request, { fetch, signal }) from fatoority sends and decodes the request. Preparation owns its data; it does not send HTTP.

    Use the Fatoora namespace. ZatcaClient.Create(config: Config) returns a client. HTTP methods block; errors throw BindingErrorException. Use using for owned objects, including child responses and optional Text values.

    Prepared requests

    Add prepare_ after fatoora_zatca_client_ in the six HTTP function names above. Inputs are identical; the output changes to FatooraComplianceRequest ** for CSR issuance, FatooraProductionRequest ** for production issuance/renewal, or FatooraInvoiceRequest ** for invoice operations.

    Request accessors use fatoora_compliance_request_, fatoora_production_request_, or fatoora_invoice_request_. method, url, and headers_json take self, char **out, and error; body uses FatooraBytes **out. decode takes self, uint16_t status, const uint8_t *body, size_t body_len, the matching credential/response output pointer, and error. The request owns its data and does not send HTTP until your transport does so.

    Ownership

    Outputs and response children are independent owned copies. Release text with fatoora_string_free; release handles with their matching _free function, such as fatoora_zatca_client_free, fatoora_csid_compliance_free, fatoora_csid_production_free, fatoora_validation_response_free, fatoora_validation_results_free, fatoora_validation_message_free, or fatoora_invoice_request_free. See C ownership and errors.
